# 1.5 Document Overview

## 1.5.1 Purpose of this Document

This Software Requirements Specification (SRS) document describes the 
complete requirements for the CampusConnect platform. It serves as the 
primary reference for the development team, project supervisor, and 
stakeholders throughout the project lifecycle.

## 1.5.2 Document Structure

This SRS document is organized into the following sections:

### 1. Introduction
Provides the purpose, scope, definitions, references, and overview of this 
SRS document.

- **1.1 Purpose**: Why this document exists and what it covers
- **1.2 Scope**: What is included and excluded from the project
- **1.3 Definitions**: Terms, acronyms, and abbreviations used
- **1.4 References**: Related documents and technical resources
- **1.5 Overview**: This section — how the document is organized

### 2. Overall Description
Provides a high-level description of the product and its environment.

- **2.1 Product Perspective**: How the product fits into its environment
- **2.2 Product Functions**: Major functions of the system
- **2.3 User Characteristics**: Who the users are
- **2.4 Constraints**: Limitations on the system
- **2.5 Assumptions**: Things assumed to be true
- **2.6 Apportioning**: How requirements are distributed

### 3. Specific Requirements
Detailed functional and non-functional requirements.

- **3.1 Functional Requirements**: What the system must do (35+ FRs)
- **3.2 Non-Functional Requirements**: Quality attributes (15+ NFRs)
- **3.3 External Interfaces**: UI, hardware, software interfaces
- **3.4 System Features**: Detailed feature descriptions

### 4. Use Cases
Detailed use case descriptions for all major interactions.

- 20+ use cases covering student, organizer, and admin interactions

### 5. Data Requirements
Database schema, data dictionary, and data retention policies.

- **5.1 Database Schema**: Firestore collections and fields
- **5.2 Data Dictionary**: Detailed field descriptions
- **5.3 Data Retention**: Data backup and deletion policies

### 6. Appendices
Supplementary information.

- **A. Glossary**: Additional terms
- **B. Analysis Models**: UML diagrams
- **C. TBD List**: Items to be determined
- **D. References**: Additional references

## 1.5.3 How to Read This Document

### For Developers:
Focus on Sections 2, 3, 4, and 5. These contain everything needed to 
implement the system.

### For Project Supervisor:
Review the entire document. Pay special attention to Section 1 (Scope) 
and Section 3 (Requirements).

### For Testers:
Focus on Sections 3 (Requirements) and 4 (Use Cases). These form the 
basis for test cases.

### For Stakeholders:
Read Section 1 (Introduction) and Section 2 (Overall Description) for a 
high-level understanding.

## 1.5.4 Document Conventions

### Terminology:
- **Shall** = Mandatory
- **Should** = Recommended
- **May** = Optional
- **Must** = Critical

### Requirement IDs:
- **FR-X-XX**: Functional Requirement (X = category)
- **NFR-XX**: Non-Functional Requirement
- **UC-XX**: Use Case

### Priority Levels:
- **High**: Must be implemented
- **Medium**: Should be implemented
- **Low**: Nice to have
